Medallion CDC, Explained
01

One change, end to end

What this platform is for, told through the story of one person changing their email address.

What are we building?

Somewhere there is an app with users. Its database, MongoDB, is busy serving that app, so it is not the place to run heavy reports.

This project copies every change from that database into a separate lakehouse, cleans it up in stages, and produces business numbers like "signups per day". The stages are called bronze, silver and gold. That three-stage pattern is the medallion architecture.

🥉

Bronze

Every change, exactly as it happened. Never edited, never deleted. Only ever appended to.

🥈

Silver

One row per user, showing their current state. Duplicates removed, deletes flagged.

🥇

Gold

Summaries a business person asks for: users by country, daily signups, users per status.

The bank-statement way of thinking

Your bank keeps a statement (every single transaction, forever), shows you a balance (where you stand right now) and sends a yearly summary (spending by category). That is bronze, silver and gold.

🥉

Why keep the raw statement at all?

If the balance is ever wrong, say from a bug in the cleaning code, you can rebuild it from the statement. Keeping an untouched, append-only history is what makes every later layer re-buildable. When you brief an AI, say "bronze is append-only, never mutate it".

That whole technique, copying every change out of a database as it happens, is called CDC (Change Data Capture).

What a Change Event actually looks like

This is a design sketch, not code from the repo yet (nothing is built). It shows the shape of one event Debezium produces for Ana.

DESIGN SKETCH 
{
  "op": "u",
  "after": "{\"_id\":\"66a1…\",\"email\":\"ana@new.com\",\"status\":\"active\"}",
  "source": { "ts_ms": 1762370000123, "ord": 4 },
  "offset": 8812
}
PLAIN ENGLISH

One event, wrapped in curly braces (that's JSON).

What happened: u = update. Others are c create, d delete, r read during the first snapshot.

The whole user document after the change, packed as text. New fields can appear here without breaking anything.

When it happened (milliseconds) and its order within that moment. Module 3 is all about these two numbers.

Its position in the Kafka queue. Used to remember "how far have I read?"

End of the event.

The description of what we want…

…its settings:

Listen to the users' Change Event topic.

Every message carries its own description of its fields, so no separate Schema Registry is needed.

Write Parquet files, which StarRocks and Spark both read natively.

Send files to our local S3 stand-in instead of Amazon.

Why not plain JSON files in bronze?

We checked StarRocks' source code: its FILES() reader handles Parquet, ORC, CSV and Avro, but not JSON. A detail like that decides the design, which is why it's written up in ADR-0004.

03

Who wins? Order, replays and deletes

The subtle part. Get this wrong and silver quietly shows old data, and nobody notices for weeks.

Postcards with postmarks

Imagine a friend sends three postcards from a trip, but the mail delivers them out of order. To know where they are now, you don't trust the order they arrived. You read the postmark.

Our postmark is the Event Position. When two Change Events for the same user compete, the higher Event Position wins.

1
Compare ts_ms

MongoDB's clock time of the change, in milliseconds.

2
Tie? Compare ord

The change's sequence number inside MongoDB's oplog.

3
Still tied? Compare the Kafka offset

Its position in the queue, as the final tiebreak.

!
A delete is final

MongoDB never reuses a user id, so nothing can come "after" a delete.

The trap we found during research

The first design said "ts_ms is the oplog timestamp". Reading Debezium's source showed it's actually MongoDB's wall clock, and that snapshot events carry the time they were read, not when the user was created.

⚠️
Verify field meanings at the source

A field name like ts_ms looks obvious and is easy to assume. When AI writes ordering logic for you, ask it to cite the docs or source for what each field means. That's how this design caught the problem before any code existed.

Two fixes came out of it: the Kafka offset as a final tiebreak, and the seeder waits for the initial snapshot to finish before it starts changing users. That way a snapshot's "read time" can never beat a real update.

Two different questions, two different numbers

🏁

"Which event wins?"

Event Position. The postmark. Decides the final state of each user.

🔖

"What haven't I read yet?"

High-Water Mark. A bookmark per Kafka partition: "I've applied up to offset 8812."

Why not use the time as the bookmark too? Bronze files from different partitions land at different moments. A "time > last time I saw" bookmark would silently skip a late file from a slower lane. ADR-0002 exists so nobody "simplifies" this back later.

The replay problem, and the guard against it

After a crash, Debezium may resend old events. They arrive with higher Kafka offsets but older Event Positions. A naive "latest file wins" update would let an old email overwrite Ana's new one.

DESIGN SKETCH 
spark.sql("""
MERGE INTO lake.silver.users s
USING latest_in_batch b ON s.user_id = b.user_id
WHEN MATCHED AND s.is_deleted = false
 AND (b.ts_ms, b.ord, b.kafka_offset) > (s.ts_ms, s.ord, s.kafka_offset)
 THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *
""")
PLAIN ENGLISH

Ask Spark to run this database command:

MERGE into the silver users table (an Iceberg table)…

…the incoming batch (already reduced to one winner per user), matched by user id.

If the user exists and isn't deleted (a delete is final)…

…and the incoming Event Position is strictly newer than the stored one…

…then overwrite the row. Replays have older positions, so they lose automatically.

A brand-new user? Insert them.

End of the command.

Without the "strictly newer" line, a replayed old event would overwrite Ana's new email. That line is the whole defence, which is why there is a dedicated replay test: reset Debezium's position, let it resend, and check silver doesn't go back in time.

Inside the Pipeline

One PySpark Pipeline does all the transformation work, and it runs right inside your local Kubernetes cluster.

A moving company that only exists during the move

A moving company sends a foreman who plans the job and a crew who carry boxes. When the truck is unloaded, everyone goes home. Nobody sits in your house waiting for the next move.

A Spark run on Kubernetes works exactly like that.

A pod is one running container. Because the crew leaves after every run, Spark only uses your Mac's memory while it is actually working.

Here are the details:

It's written in Python, so PySpark.

Use our own container image, with Spark, Iceberg, the StarRocks connector and our code inside.

Don't download it from the internet: kind already has it (we copied it in with kind load).

Which script to run.

The foreman gets 1 CPU and 1 GB of memory…

…and one crew member with 1 GB. Small on purpose: the whole platform has to fit in 16 GB.

One run, three steps

1
bronze_to_silver

Read only the bronze files beyond the High-Water Mark, pick the winning event per user, MERGE into the Iceberg silver table, then move the bookmark forward.

2
checks

Data checks on silver: every user_id unique and present, every status one of active, inactive or suspended. If any check fails, the run stops here.

3
silver_to_gold

Build the three Gold Metrics and publish them to StarRocks, all at once, so readers never see a half-built table.

Publishing gold without a "half-built" moment

The StarRocks connector for Spark can only add rows; it can't replace a table. So the Pipeline builds a hidden copy, then swaps it in. A design sketch:

DESIGN SKETCH · silver_to_gold.py 
df = (spark.table("lake.silver.users")
      .where(~F.col("is_deleted"))
      .groupBy("country", "status")
      .agg(F.count("*").alias("users")))
write_staging(df, "gold.users_by_country_stg")
swap("users_by_country", "users_by_country_stg")
PLAIN ENGLISH

Load silver into a DataFrame.

Skip Deleted Users (this metric is about current users).

Group by country and status…

…and count.

Write the result into a hidden staging table in StarRocks.

Swap staging and live gold in one step (ALTER TABLE … SWAP WITH). Readers see the old version, then the new one, never anything in between.

💡
Build aside, then swap

Building the new version next to the old one and switching over in one move is called an atomic swap. It's the same idea as blue/green deployments. When AI writes code that replaces data people are reading, ask: "is the switch-over atomic, or will readers see an empty table?"

What we keep, and what we gave up

Written in PySpark (checks.py) instead of dbt tests. A failed check fails the run, and gold keeps its previous version.

🧪

Unit tests

pytest with a local Spark session: Event Position winner, delete is final, replay ignored, New Attribute flattening.

🗺️

Lineage

No automatic graph anymore. Run traces (module 5) and the README show which step builds which table.

And the New Attribute promise still stands: when the app starts sending phone, silver gains a phone column with zero code changes. It's one of the spikes to prove first.

An alarm, translated

Alerts are rules stored in the repo. A design sketch of one:

DESIGN SKETCH 
- alert: CdcLagHigh
  expr: debezium_millis_behind_source > 300000
  for: 5m
  labels: { severity: warning }
PLAIN ENGLISH

An alarm named "CDC lag is high".

Fire when Debezium is more than 5 minutes (300,000 ms) behind MongoDB…

…and has stayed that way for 5 minutes, so a short blip doesn't raise a false alarm.

Mark it as a warning. In this POC it only shows in Grafana. Nobody gets paged.

Laptop today, EKS tomorrow

kind→ Amazon EKS (managed Kubernetes)

StarRocks operator→ StarRocks on EKS (shared-data on S3)
🔐
The MCP server can write

The official StarRocks MCP server always exposes a write_query tool. The only protection is the database user: mcp_reader gets SELECT on gold and nothing else. When you connect an AI to data, enforce limits in the database, not just in the prompt.
