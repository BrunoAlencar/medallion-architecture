Inside the Pipeline

One PySpark Pipeline does all the transformation work, and it runs right inside your local Kubernetes cluster.

A moving company that only exists during the move

A moving company sends a foreman who plans the job and a crew who carry boxes. When the truck is unloaded, everyone goes home. Nobody sits in your house waiting for the next move.

A Spark run on Kubernetes works exactly like that.

A pod is one running container. Because the crew leaves after every run, Spark only uses your Mac's memory while it is actually working.

How you ask for a run

You don't start Spark by hand. You hand Kubernetes a description of the job, and the Spark Operator makes it happen. A design sketch:

DESIGN SKETCH 
kind: SparkApplication
spec:
  type: Python
  image: medallion/spark:dev
  imagePullPolicy: Never
  mainApplicationFile: local:///opt/app/bronze_to_silver.py
  driver:   { cores: 1, memory: "1g" }
  executor: { instances: 1, memory: "1g" }
PLAIN ENGLISH

"I want a Spark job," as a Kubernetes resource.

Here are the details:

It's written in Python, so PySpark.

Use our own container image, with Spark, Iceberg, the StarRocks connector and our code inside.

Don't download it from the internet: kind already has it (we copied it in with kind load).

Which script to run.

The foreman gets 1 CPU and 1 GB of memory…

…and one crew member with 1 GB. Small on purpose: the whole platform has to fit in 16 GB.

One run, three steps

1
bronze_to_silver

Read only the bronze files beyond the High-Water Mark, pick the winning event per user, MERGE into the Iceberg silver table, then move the bookmark forward.

2
checks

Data checks on silver: every user_id unique and present, every status one of active, inactive or suspended. If any check fails, the run stops here.

3
silver_to_gold

Build the three Gold Metrics and publish them to StarRocks, all at once, so readers never see a half-built table.

Publishing gold without a "half-built" moment

The StarRocks connector for Spark can only add rows; it can't replace a table. So the Pipeline builds a hidden copy, then swaps it in. A design sketch:

DESIGN SKETCH · silver_to_gold.py 
df = (spark.table("lake.silver.users")
      .where(~F.col("is_deleted"))
      .groupBy("country", "status")
      .agg(F.count("*").alias("users")))
write_staging(df, "gold.users_by_country_stg")
swap("users_by_country", "users_by_country_stg")
PLAIN ENGLISH

Load silver into a DataFrame.

Skip Deleted Users (this metric is about current users).

Group by country and status…

…and count.

Write the result into a hidden staging table in StarRocks.

Swap staging and live gold in one step (ALTER TABLE … SWAP WITH). Readers see the old version, then the new one, never anything in between.

💡
Build aside, then swap

Building the new version next to the old one and switching over in one move is called an atomic swap. It's the same idea as blue/green deployments. When AI writes code that replaces data people are reading, ask: "is the switch-over atomic, or will readers see an empty table?"

What we keep, and what we gave up

dbt was dropped (ADR-0005), so a few things it would have given us for free are now our job:

✅

Data checks

Written in PySpark (checks.py) instead of dbt tests. A failed check fails the run, and gold keeps its previous version.

🧪

Unit tests

pytest with a local Spark session: Event Position winner, delete is final, replay ignored, New Attribute flattening.

🗺️

Lineage

No automatic graph anymore. Run traces (module 5) and the README show which step builds which table.

And the New Attribute promise still stands: when the app starts sending phone, silver gains a phone column with zero code changes. It's one of the spikes to prove first.
