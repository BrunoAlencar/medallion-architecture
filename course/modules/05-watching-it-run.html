A hospital monitor for data

A patient monitor shows heart rate, a printout records events, and an alarm beeps when something crosses a line. The LGTM stack plays all three roles for our platform.

📈

Numbers over time: Kafka lag, run durations, rows processed. These are the vital signs.

Every line each program prints. Where you read the actual error.

🧵

One trace per Pipeline run, with a span per step: bronze_to_silver, checks, silver_to_gold.

The headline number is Pipeline Lag: the time from a change happening in MongoDB to it showing up in silver. If it climbs, the dashboard's earlier panels (CDC lag, bronze freshness) tell you which stage is behind.

An alarm, translated

Alerts are rules stored in the repo. A design sketch of one:

DESIGN SKETCH 
- alert: CdcLagHigh
  expr: debezium_millis_behind_source > 300000
  for: 5m
  labels: { severity: warning }
PLAIN ENGLISH

An alarm named "CDC lag is high".

Fire when Debezium is more than 5 minutes (300,000 ms) behind MongoDB…

…and has stayed that way for 5 minutes, so a short blip doesn't raise a false alarm.

Mark it as a warning. In this POC it only shows in Grafana. Nobody gets paged.

Laptop today, EKS tomorrow

Every local piece was chosen because it has an AWS counterpart:

kind→ Amazon EKS (managed Kubernetes)
SeaweedFS→ Amazon S3, with IRSA for credentials
Strimzi + Connect→ Amazon MSK + MSK Connect, or Strimzi on EKS
Lakekeeper→ AWS Glue Data Catalog
Spark Operator→ EMR on EKS
StarRocks operator→ StarRocks on EKS (shared-data on S3)
🔐
The MCP server can write

The official StarRocks MCP server always exposes a write_query tool. The only protection is the database user: mcp_reader gets SELECT on gold and nothing else. When you connect an AI to data, enforce limits in the database, not just in the prompt.

Test the risky assumptions first

Before building the whole thing, the plan starts with four small spikes. Any of these failing changes the design:

a
Aiven sink on Kafka 4.3

Parquet output, S3 path-style requests to SeaweedFS, and the dt=/hr= folder layout.

b
The MERGE adds New Attribute columns by itself

Spark 4.1 + Iceberg 1.12 adding a phone column with no manual change.

c
StarRocks shared-data on SeaweedFS

Plus the Spark connector writing a staging table that is then swapped in.

d
Mimir as one pod

No official single-binary chart exists.
