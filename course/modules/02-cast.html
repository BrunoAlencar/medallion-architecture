Meet the cast

A handful of components, one newsroom. Knowing who does what lets you tell an AI exactly where a change belongs.

Think of it as a newsroom

A newsroom has a stenographer in the courtroom, a wire service that moves stories, an archive in the basement, an editor who rewrites, and a newsstand where readers buy the paper. Our platform has exactly those jobs.

🍃
MongoDB: the courtroom

Where things actually happen. The app writes users here.

👂
Debezium: the stenographer

Writes down every change MongoDB makes, in order, without interrupting.

📬
Kafka: the wire service

A durable queue that carries events from the people who write them to whoever reads them.

🗄️
Aiven S3 sink + RustFS: the archive

The sink files each batch of events into the bronze shelf of an S3-compatible store.

✍️
PySpark: the editor

Turns the raw archive into a clean silver table, then writes the gold summaries.

📰
StarRocks: the newsstand

A fast query engine where gold lives and where people (and AI tools) read results.

Everything runs inside a local Kubernetes cluster created by kind, so it behaves like Amazon EKS without the bill.

How the archivist is configured

Components like the sink aren't programmed, they're configured. A design sketch of the bronze sink's settings (based on the plan, not yet tested):

DESIGN SKETCH 
kind: KafkaConnector
spec:
  config:
    topics: cdc.app.users
    value.converter.schemas.enable: true
    format.output.type: parquet
    format.output.fields: key,value,offset,timestamp
    aws.s3.endpoint: http://rustfs.data:9000
PLAIN ENGLISH

"Please create a connector." This is a Kubernetes resource, handled by the Strimzi operator.

The description of what we want…

…its settings:

Listen to the users' Change Event topic.

Every message carries its own description of its fields, so no separate Schema Registry is needed.

Write Parquet files, which StarRocks and Spark both read natively.

Store the Kafka offset next to each event, so pipelines can remember how far they've read.

Send files to our local S3 stand-in instead of Amazon.

🧭
Why not plain JSON files in bronze?

We checked StarRocks' source code: its FILES() reader handles Parquet, ORC, CSV and Avro, but not JSON. A detail like that decides the design, which is why it's written up in ADR-0004.
