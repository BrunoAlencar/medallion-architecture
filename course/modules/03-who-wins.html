Who wins? Order, replays and deletes

The subtle part. Get this wrong and silver quietly shows old data, and nobody notices for weeks.

Postcards with postmarks

Imagine a friend sends three postcards from a trip, but the mail delivers them out of order. To know where they are now, you don't trust the order they arrived. You read the postmark.

Our postmark is the Event Position. When two Change Events for the same user compete, the higher Event Position wins.

1
Compare ts_ms

MongoDB's clock time of the change, in milliseconds.

2
Tie? Compare ord

The change's sequence number inside MongoDB's oplog.

3
Still tied? Compare the Kafka offset

Its position in the queue, as the final tiebreak.

!
A delete is final

MongoDB never reuses a user id, so nothing can come "after" a delete.

The trap we found during research

The first design said "ts_ms is the oplog timestamp". Reading Debezium's source showed it's actually MongoDB's wall clock, and that snapshot events carry the time they were read, not when the user was created.

⚠️
Verify field meanings at the source

A field name like ts_ms looks obvious and is easy to assume. When AI writes ordering logic for you, ask it to cite the docs or source for what each field means. That's how this design caught the problem before any code existed.

Two fixes came out of it: the Kafka offset as a final tiebreak, and the seeder waits for the initial snapshot to finish before it starts changing users. That way a snapshot's "read time" can never beat a real update.

Two different questions, two different numbers

🏁

"Which event wins?"

Event Position. The postmark. Decides the final state of each user.

🔖

"What haven't I read yet?"

High-Water Mark. A bookmark per Kafka partition: "I've applied up to offset 8812."

Why not use the time as the bookmark too? Bronze files from different partitions land at different moments. A "time > last time I saw" bookmark would silently skip a late file from a slower lane. ADR-0002 exists so nobody "simplifies" this back later.

The replay problem, and the guard against it

After a crash, Debezium may resend old events. They arrive with higher Kafka offsets but older Event Positions. A naive "latest file wins" update would let an old email overwrite Ana's new one.

DESIGN SKETCH 
spark.sql("""
MERGE INTO lake.silver.users s
USING latest_in_batch b ON s.user_id = b.user_id
WHEN MATCHED AND s.is_deleted = false
 AND (b.ts_ms, b.ord, b.kafka_offset) > (s.ts_ms, s.ord, s.kafka_offset)
 THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *
""")
PLAIN ENGLISH

Ask Spark to run this database command:

MERGE into the silver users table (an Iceberg table)…

…the incoming batch (already reduced to one winner per user), matched by user id.

If the user exists and isn't deleted (a delete is final)…

…and the incoming Event Position is strictly newer than the stored one…

…then overwrite the row. Replays have older positions, so they lose automatically.

A brand-new user? Insert them.

End of the command.

Without the "strictly newer" line, a replayed old event would overwrite Ana's new email. That line is the whole defence, which is why there is a dedicated replay test: reset Debezium's position, let it resend, and check silver doesn't go back in time.
