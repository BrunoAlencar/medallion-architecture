# Project state and stack verification

_Researched 2026-11-05. Every version below was fetched on that date from the linked primary source (GitHub releases/tags/source, official docs, PyPI, Maven Central, Docker Hub, Confluent Hub API). Nothing is from memory._

**Bottom line.** The design mostly holds, with three hard contradictions:

1. StarRocks `FILES()` cannot read JSON at all, gzip or not.
2. The StarRocks Spark connector cannot overwrite.
3. There is no single-binary Helm chart for Mimir.

There is also one environment-level blocker: MinIO's public images are gone. One modeling problem affects both Pipelines: Debezium's `source.ts_ms` is not the oplog timestamp. Details are in sections 4 and 6.

## 2. Settled design (from the Q&A; it overrides PLAN.md)

- **Source.** A MongoDB single-node replica set holds the `users` collection. A seeder inserts about 5k Users *before* the Debezium connector starts, so snapshot `r` events are produced. It then keeps inserting, updating and deleting, and adds New Attributes over time (`phone`, nested ones). Fields: `_id, name, email, country (ISO-2), status {active, inactive, suspended}, created_at, updated_at, address{city, zip}`.
- **CDC.** Debezium MongoDB source with `capture.mode=change_streams_update_full`, full envelope kept. Kafka runs on Strimzi in KRaft mode, with 3 partitions keyed by `_id`. The Confluent S3 sink writes JSON.gz to MinIO `bronze`, hourly partitions, append-only, with an InsertField SMT adding Kafka partition and offset. Tombstones are handled.
- **Ordering.** Oplog Position (`source.ts_ms` + `source.ord`) decides which Change Event wins. The High-Water Mark is the Kafka offset per partition, shared by both Pipelines (ADR-0002).
- **Silver.** Soft delete (`is_deleted`, `deleted_at`). New Attributes land as STRING columns, flattened with `_`, and are never dropped. No SCD2 in v1.
- **PySpark Pipeline.** Runs on the Spark Operator. Silver is Iceberg on MinIO via Lakekeeper REST (+ Postgres), with Glue in prod. Gold goes to StarRocks DB `gold_pyspark` through the StarRocks Spark connector.
- **dbt Pipeline.** dbt Core + `dbt-starrocks`. It reads bronze with StarRocks `FILES()` (fallback: Parquet sink). Silver is a StarRocks Primary Key table and gold goes to `gold_dbt`. StarRocks runs shared-data on MinIO via the StarRocks Kubernetes Operator (1 FE + 1 CN). Prod target is StarRocks on EKS.
- **Gold Metrics.** `users_by_country` (non-deleted, by status), `daily_signups` (all Users by `created_at`, deleted included), `user_status_summary` (non-deleted per status + a deleted row).
- **Change scenarios for COMPARISON.md.** (1) New Attribute `phone` with zero code change, (2) new Gold Metric `users_by_city`, (3) promote `phone` to a validated type.
- **Observability.** Full LGTM with Loki, Grafana, Tempo and Mimir as separate single-binary Helm charts on MinIO buckets. Alloy is the only collector. Pipelines push OTLP metrics and traces: one trace per run, one span per step, with dbt spans built from `run_results.json`. Exporters: Strimzi JMX, Kafka Exporter, Debezium JMX, percona mongodb_exporter, MinIO metrics, Spark PrometheusServlet and StarRocks `/metrics`. Dashboards are kept as code, and alerts have no notification channel.
- **MCP (later).** A read-only StarRocks user `mcp_reader` with SELECT on `gold_dbt` only, used by `mcp-server-starrocks`.
- **Machine.** Apple M5 Pro (arm64), 24 GB RAM, 15 CPUs. Docker budget is 16 GB / 8 CPUs, with Makefile profiles `up` and `up-core`. Docker, kubectl, helm and kind are not installed yet.

### Notes on Contradicted and Unclear items, and what they change

**1. `FILES()` cannot read JSON. This breaks the dbt bronze read.**
In the released 4.1.7 source, the format allow-list for `FILES()` loading is `parquet, orc, csv, avro`. The error message even says "Use any of (parquet, orc, csv)" ([source](https://github.com/StarRocks/starrocks/blob/4.1.7/fe/fe-core/src/main/java/com/starrocks/catalog/TableFunctionTable.java)), and the docs agree. The stated fallback, a Parquet sink, is *also* blocked as written: the Confluent S3 sink requires Avro, Protobuf or JSON-Schema converters for Parquet, which means a Schema Registry ([overview](https://docs.confluent.io/kafka-connectors/s3-sink/current/overview.html)). Options, best first:

- **(a) Spike `FILES()` with `format=csv` over `*.json.gz`.** Read each NDJSON line as one VARCHAR column, using a column separator that never occurs (e.g. `\x01`) and no enclose. Then `parse_json()` / `get_json_string()` in the staging model. The source shows `.gz` maps to `FORMAT_CSV_GZ` ([Load.java](https://github.com/StarRocks/starrocks/blob/4.1.7/fe/fe-core/src/main/java/com/starrocks/load/Load.java)), and the FILES doc has a `csv.gz` example. However, the feature table says CSV compression via FILES is "To be supported". **Unclear until tested.** It keeps bronze unchanged and needs no new components.
- **(b) Parquet sink + a Schema Registry.** Debezium would emit Avro (e.g. Apicurio Registry, which has a Confluent-compatible API). This adds a component and changes the bronze format, which also changes the PySpark reader.
- **(c) Uncompressed JSON + Broker Load into a StarRocks staging table.** Broker Load supports JSON since v3.2.3, but gzip JSON exists only on `main` ([PR #61786](https://github.com/StarRocks/starrocks/pull/61786)). Broker Load is an async job, not a SELECT, so dbt would drive it from a macro or `run-operation`. This weakens the "dbt reads bronze" story.

Whatever is chosen, record it in a new ADR and keep PySpark reading the same bronze.

**2. Debezium `source.ts_ms` is the MongoDB wall time, not the oplog timestamp. This affects GLOSSARY "Oplog Position" and both Pipelines.**
Since Debezium 3.4.0.Final ([DBZ-9683](https://github.com/debezium/debezium/commit/981d29ab0d3b8df1d6659ac569c266dd08b993ea)), `source.ts_ms` is the change event's `wallTime` in ms (MongoDB 6.0+). `source.ord` is still the clusterTime *increment* ([SourceInfo.java](https://github.com/debezium/debezium/blob/v3.7.0.Final/debezium-connector-mongodb/src/main/java/io/debezium/connector/mongodb/SourceInfo.java)). So (`ts_ms`, `ord`) is not literally "(seconds, increment)" as GLOSSARY defines it, and the true clusterTime seconds are not in the envelope. Ordering by (`ts_ms`, `ord`) is usually right on a single-node replica set, because the primary's wall clock moves with clusterTime, but it is not a guaranteed total order. Snapshot `r` events carry the *read-time* clock ([DBZ-8708](https://github.com/debezium/debezium/commit/5ad65c4d1cd4d4d0ffe21cce2152420acfdf2335)).

What this changes:
- Within a partition, the Kafka offset is the exact emit order, so use `(ts_ms, ord, kafka_offset)` as a tiebreak.
- Make the seeder wait until the snapshot completes before mutating.
- Consider rewording GLOSSARY "Oplog Position" to say what fields actually carry it.
- Note that resume tokens in source metadata ([dbz#718 commit](https://github.com/debezium/debezium/commit/a89851ed2149b7d73e61e60aabb87129d561d264)) landed *after* 3.7.0.Final.

**3. dbt silver on a PK table can regress on replayed events.**
Debezium may duplicate events after a Connect failure ([mongodb.adoc](https://github.com/debezium/debezium/blob/v3.7.0.Final/documentation/modules/ROOT/pages/connectors/mongodb.adoc)). A replay lands at a *higher* Kafka offset with an *older* Oplog Position. ADR-0003 dedupes only within a batch, and PK INSERTs are last-write-wins with no `merge_condition` ([PK docs](https://github.com/StarRocks/starrocks/blob/main/docs/en/loading/Load_to_Primary_Key_tables.md)). A replay processed in a later run would therefore overwrite newer state. The dbt model should also drop incoming rows whose Oplog Position ≤ the stored one in `{{ this }}`. ADR-0003's "safe because ... read in order" holds only without replays.

**4. The Spark connector cannot overwrite gold.**
Use one of these instead:
- (a) `TRUNCATE TABLE` over the MySQL protocol, then append. This is not atomic.
- (b) Append into a staging table, then `ALTER TABLE gold SWAP WITH staging`. This is atomic. The SWAP semantics are not verified here.
- (c) Make gold PK tables keyed by the metric's dimensions and upsert. Stale keys (e.g. a country with zero Users) would linger unless they are deleted.

**5. Mimir has no single-binary chart.**
The choices are:
- Run Mimir monolithic (`-target=all`) from your own Deployment/StatefulSet manifest ([deployment modes](https://grafana.com/docs/mimir/latest/references/architecture/deployment-modes/)).
- Or accept `mimir-distributed` with Kafka and many components turned down. That is costly against a 16 GB budget.

Whether Mimir 3.x monolithic needs ingest-storage/Kafka by default was **not** confirmed from a primary source. Check it in the Mimir 3.2 config reference before building.

**6. MinIO is gone from public registries.**
Pick an S3-compatible replacement before writing manifests:
- [`pgsty/silo`](https://github.com/pgsty/silo) is a MinIO fork (AGPL-3.0, multi-arch, `RELEASE.2026-10-26T00-00-00Z`). It is what Mimir's chart uses.
- [RustFS](https://github.com/rustfs/rustfs) is Apache-2.0.

MinIO-specific bits (`mc mb`, `/minio/v2/metrics/*`, STS for Lakekeeper vended credentials) must be re-verified against the fork. "MinIO native metrics" is **Unclear** for any fork.

**7. dbt and New Attributes.**
Because `after` is a JSON string, "New Attribute with zero code change" needs dynamic key discovery in SQL: query the distinct JSON keys, then add columns. dbt-starrocks does pass `on_schema_change` through `process_schema_changes` ([incremental.sql](https://github.com/StarRocks/dbt-starrocks/blob/main/dbt/include/starrocks/macros/materializations/models/incremental.sql)). However, it has no StarRocks-specific `alter_relation_add_remove_columns` macro and no test of `append_new_columns`, so it relies on the dbt-adapters default DDL. **Unclear**: spike before scenario 1.

**8. Lakekeeper + StarRocks credentials.**
Lakekeeper's StarRocks guide targets 3.3 with static keys ([engines](https://docs.lakekeeper.io/docs/nightly/engines/)). StarRocks ≥4.0 supports vended credentials ([iceberg.md](https://github.com/StarRocks/starrocks/blob/main/docs/en/data_source/catalog/iceberg/iceberg.md)), but vended credentials against a MinIO-fork STS is **Unclear**. Use static keys for StarRocks and vended or remote-signing for Spark.

## 6. Open risks

1. **dbt bronze read is unresolved** (section 4, note 1). Nothing in released StarRocks reads gzip JSON from S3 via SQL. Spike the CSV-over-`.json.gz` trick first. If it fails, decide between Schema Registry + Parquet and Broker Load, and write an ADR.
2. **Ordering key semantics** (note 2). `ts_ms` is wall time. Define the winner as `(ts_ms, ord)` with a Kafka-offset tiebreak, gate the seeder on snapshot completion, and update GLOSSARY wording.
3. **Replay regression in dbt silver** (note 3). Compare against stored Oplog Position, not just within a batch. The same applies to the PySpark Iceberg MERGE condition.
4. **Gold overwrite in PySpark** (note 4). An extra step is needed (TRUNCATE or SWAP via JDBC), which counts against PySpark in COMPARISON.md.
5. **Object storage replacement** (note 6). This affects bucket-init, LGTM storage, Lakekeeper STS and the "MinIO native metrics" exporter.
6. **Mimir footprint** (note 5). A hand-rolled monolithic deployment, or a heavy `mimir-distributed` (Kafka on by default).
7. **Memory.** StarRocks examples assume FE 16Gi and CN 64Gi, while the quick start runs in 4 GB. Kafka + Connect + StarRocks + Spark driver/executor + Lakekeeper/Postgres + four LGTM services + Alloy must fit in 16 GB. Size FE/CN JVMs explicitly and keep LGTM and Spark out of `up-core`.
8. **Iceberg write path from StarRocks.** UPDATE/MERGE on Iceberg need StarRocks 4.2 (unreleased), so all Iceberg upserts stay in Spark. That is fine because ADR-0003 already has PySpark own Iceberg.
9. **dbt-starrocks maturity.** The README says "under development". There is no merge strategy, `append_new_columns` is untested, and releases are roughly quarterly.
10. **Short-lived Spark jobs and scraping.** PrometheusServlet lives on the driver UI (`:4040`) only while the app runs ([Spark monitoring](https://spark.apache.org/docs/latest/monitoring.html)). The OTLP push from the pipeline is the real signal, and scraping Spark may yield little.
11. **MCP has no read-only mode.** `write_query` always exists, and `query_and_plotly_chart` evaluates a caller-supplied Python expression ([README](https://github.com/StarRocks/mcp-server-starrocks/blob/v0.4.0/README.md)). The `mcp_reader` SELECT-only grant is the only guard, so keep it strict.
12. **Strimzi `v1` CRDs.** Many blog and older examples use `kafka.strimzi.io/v1beta2`, which Strimzi 1.x rejects ([CHANGELOG](https://github.com/strimzi/strimzi-kafka-operator/blob/1.3.1/CHANGELOG.md)).
13. **Helm chart sources moved.** Grafana, Loki and Tempo now come from `grafana-community`. Alloy and Mimir stay on `grafana`.
14. **Confluent S3 sink licence and runtime.** The Confluent Community License is fine for a POC, but compatibility with the Kafka 4.3 Connect runtime is not documented. Verify at first boot.
